# SP004 — N+1 tespit algoritması

Durum: ✅
Task: [T004_0](../tasks/T004_0.md)

## Amaç

Projenin çekirdeği. SELECT loglarından N+1 potansiyeli taşıyan istekleri
deterministik olarak çıkarmak.

## Algoritma

1. Seçilen zaman aralığındaki SELECT logları alınır
2. correlationId bazında gruplanır
3. Her grup kendi çalıştırılma sırasına göre incelenir
4. SQL'ler normalize edilir (bind değerleri `?`)
5. Foreign key metadata ile parent-child ilişkisi olan sorgular belirlenir
6. Her parent-child çifti için dört koşul:
  - Parent sorgu child'dan **önce** mi çalışmış?
  - Child sorgular aynı normalize şablona mı sahip?
  - Aynı şablon eşik değerinden (varsayılan 5) fazla mı tekrar etmiş?
7. Üçü de sağlanıyorsa o correlationId için bulgu üretilir
8. Child sorguların bind ettiği FK değerlerinin ne kadar farklı olduğu **güven
   düzeyine** yansır (aşağıdaki ister), bulgunun üretilmesini engellemez

## İsterler

- Tespit tamamen deterministik olmalı; model kullanılmamalı.
- Eşik değeri config'ten ayarlanabilmeli.
- Bulgu, raporun istediği tüm alanları taşımalı.
- Aynı istek içinde birden fazla bulgu çıkabilmeli.
- Bind değerleri büyük ölçüde tekrar ediyorsa bu, güven düzeyine yansımalı —
  aynı id'nin tekrar tekrar sorgulanması N+1 değil, eksik cache'tir.
- Bulgu, FK kolonuna bind edilen **tüm** distinct değerleri taşımalı; rapor
  ekranında kanıt kırpılmış görünmemeli.

## Kabul kriterleri

- [x] N+1 üreten istekte bulgu çıkıyor
- [x] Temiz (join fetch'li) istekte bulgu çıkmıyor
- [x] Eşik altındaki tekrarlar bulgu üretmiyor
- [x] Bind değerleri aynıysa güven düşüyor
- [x] Bulgudaki bind değerleri kırpılmadan, tamamı raporda görünüyor
- [x] Parent sorgu child'dan sonra çalışmışsa bulgu üretilmiyor
- [x] Algoritma birim testleriyle kapalı, model çağrısı yok
