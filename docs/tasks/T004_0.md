# T004_0 — N+1 tespit algoritması

Feature: [SP004](../features/SP004.md) · Repo: api-debug-agent

Saf Java. Bu task projenin çekirdeği — model tarafına geçmeden önce bunun
testlerle kapalı olması gerekiyor.

## Tipler

```java
record Finding(
    String  correlationId,
    String  endpoint,           // RequestInfo'dan
    String  parentTable,
    String  childTable,
    String  foreignKey,         // "payment.customer_id -> customer.id"
    String  normalizedQuery,    // tekrarlayan child şablonu
    int     repeatCount,
    int     distinctBindCount,
    Confidence confidence,      // HIGH | MEDIUM
    List<String> bindValues,    // FK'ye bind edilen tüm distinct değerler
    long    parentSeq,          // sıralama kanıtı
    long    firstChildSeq
) {}
```

## Adımlar

1. `analysis/NPlusOneDetector.detect(List<ExecutedQuery>, List<RequestInfo>)`
   → `List<Finding>`
2. correlationId bazında grupla, her grubu `seq` (T003_0) ile sırala.
3. Her grup içinde:
    - Her sorguyu `SqlAnalyzer.parse` ile çöz, `parsed=false` olanları atla
    - Normalize şablona göre grupla, tekrar sayısını çıkar
4. **Child adayı** bulma: bir şablonun WHERE'inde `ForeignKeyCache` ile eşleşen
   parametreli eşitlik varsa (`payment.customer_id` → `customer.id`), o şablon
   child adayıdır. `parentTable` FK'nin işaret ettiği tablodur.
5. **Parent bulma:** aynı grup içinde `parentTable`'dan okuyan ve child'ın ilk
   koşusundan **önce** (`seq` küçük) çalışmış bir sorgu ara. Yoksa bulgu üretme.
6. Dört koşulu uygula:
   | Koşul | Kontrol |
   |---|---|
   | Sıra | `parent.seq < firstChild.seq` |
   | Aynı şablon | zaten gruplama gereği |
   | Farklı bind | `distinctBindCount > 1` |
   | Eşik | `repeatCount >= analysis.n-plus-one.min-repeat` |
7. `distinctBindCount`: child sorguların FK kolonuna bind edilen değerlerin
   benzersiz sayısı. Bind pozisyonunu WHERE'deki parametre sırasından bul.
8. Güven düzeyi:
    - `HIGH`: `distinctBindCount >= repeatCount * 0.9`
    - `MEDIUM`: altındaysa — tekrar eden id'ler var, N+1'den çok cache eksikliği
      olabilir. Bulgu yine üretilir, güven düşer.
9. Birim testleri, `ExecutedQuery` listesi elle kurularak:
    - Klasik N+1: 1 parent + 200 farklı bind'li child → HIGH
    - Join fetch: tek sorgu → bulgu yok
    - 3 tekrar (eşik altı) → bulgu yok
    - Aynı bind 200 kez → MEDIUM
    - Child parent'tan önce → bulgu yok
    - Aynı istekte iki ayrı N+1 → iki bulgu

## Doğrulama

- Birim testleri yeşil
- Gerçek bir N+1 koşusunda `repeatCount` log'daki tekrarla birebir tutuyor
- Temiz endpoint'te bulgu çıkmıyor

## Tuzaklar

- Parent sorguyu "aynı tablodan okuyan ilk sorgu" diye alma; `seq`
  karşılaştırmasını gerçekten yap. Sıra koşulu algoritmanın yanlış pozitifleri
  eleyen kısmı.
- Eşiği koda gömme, config'ten oku.
- Bind pozisyonu: sorguda birden fazla `?` varsa FK'ye karşılık geleni bul,
  körü körüne ilkini alma.

## Kararlar

- **"Farklı bind" sert koşul değil, güven düzeyine devredildi.** Adım 6'daki
  `distinctBindCount > 1` kapısı kaldırıldı; SP004 kabul kriteri "bind değerleri
  aynıysa **güven düşüyor**" diyor, "bulgu üretilmiyor" değil. `distinctBindCount`
  1 olsa bile eşik aşılmışsa bulgu çıkar, `confidence = MEDIUM` olur. Kalan üç
  koşul (sıra, aynı şablon, eşik) sert kapı olarak duruyor.
- **`SqlAnalyzer.EqualityPredicate`'e `parameterIndex` eklendi.** Bind pozisyonu
  başka türlü bilinemiyordu: predicate listesi JSqlParser AST'sini stack ile
  gezdiği için kaynak sırasında değil, dolayısıyla listedeki sıra bind sırasının
  yerine geçmiyor. JSqlParser'ın `JdbcParameter.getIndex()` değeri 1-tabanlı ve
  kaynak sırasında — Hibernate'in `binding parameter (2:BIGINT)` log'undaki index
  ile birebir örtüşüyor (`SqlAnalyzerTest`'te doğrulandı). Index'i `null` olan
  predicate listeye hiç girmiyor; pozisyonu bilinmeyen bir eşitliği raporlamaktansa
  düşürmek doğru.
- **Parent seçimi: child'ın ilk koşusundan önceki, `seq`'i en büyük olan sorgu.**
  "Aynı tablodan okuyan ilk sorgu" değil — child'a en yakın önceki parent.
  Aday, child şablonunun kendi koşularından biri olamaz.
- **FK bind'i çözülemeyen child koşusu sayıma girmez.** Ne `repeatCount`'a ne de
  `distinctBindCount`'a. Eksik bind log'u yüzünden yanlış bir sayıya bağlanmaktansa
  o koşuyu saymamak yeğ.
- **Bind pozisyonu her koşu için kendi parse'ından çözülür**, şablonun ilk
  koşusundan değil. Aynı normalize şablona düşen iki ham SQL'de parametre
  dizilimi teorik olarak farklı olabilir.
- **Bir şablonda birden fazla FK eşitliği varsa her biri ayrı parent-child çifti**
  olarak değerlendirilir (SP004: "her parent-child çifti için dört koşul").
- **`SchemaUnavailableException` yakalanmıyor.** FK metadata yokken "bulgu yok"
  demek yanıltıcı olurdu; karar `AnalysisService`'e bırakıldı.
- **Eşik `analysis.n-plus-one.min-repeat`'ten okunuyor** (`NPlusOneProperties`),
  koda gömülü değil — testle de kapalı.
- **`endpoint` = `method + " " + path`.** `RequestInfo`'da query string alanı yok.
  Eşleşen `RequestInfo` yoksa `endpoint` null, bulgu yine üretilir.
- **Bind değerleri kırpılmıyor; alan adı `bindValues`.** Başlangıçta bulgu yalnızca
  ilk 5 değeri (`MAX_SAMPLE_BINDS`) taşıyordu ve rapor ekranında geri kalan bind'ler
  görünmüyordu — kanıtın kırpılmış hali kullanıcıya yanıltıcı geliyor. Sabit kaldırıldı,
  bulgu FK kolonuna bind edilen **tüm distinct değerleri** ilk görülme sırasında taşıyor
  (`LinkedHashSet` sırası korunuyor). Alan `sampleBinds` → `bindValues` olarak yeniden
  adlandırıldı; artık "örnek" değil, tamamı. Üst sınır konmadı: kanıtın eksiksiz olması
  rapor JSON'unun boyutundan önce geliyor. Modele giden `EnrichmentInput` bu alanı zaten
  taşımıyor, dolayısıyla token bütçesi etkilenmiyor.
- **Uçtan uca doğrulama** `NPlusOneDetectorLiveTest` ile yapıldı: `DEMO_API_LIVE`
  env değişkeni ile açılıyor, `/api/customers/detail` (N+1) ve
  `/api/customers/overview` (join fetch) endpoint'lerini gerçek `demo-api` üstünde
  çağırıp log → assemble → detect zincirini çalıştırıyor. `repeatCount` log'daki
  gerçek tekrar sayısıyla birebir tutuyor, temiz endpoint'te bulgu çıkmıyor.
