# T001_1 — Çok sağlayıcılı model erişimi

Feature: [SP001](../features/SP001.md) · Repo: api-debug-agent

## Adımlar

1. `llm/ChatClientLlmClient` — modele giden **tek** giriş noktası, beton sınıf,
   arayüz yok. Model erişimi ham `ChatModel` yerine
   `org.springframework.ai.chat.client.ChatClient` üzerinden.
   ```java
   LlmResult ask(String promptName, Map<String,Object> vars);
   ```
   Hem sağlayıcı yönlendirmesi hem model belirleme burada: `llm.enabled`
   kontrolü, `llm.provider` → `ChatClient` seçimi, `llm.providers.<ad>` →
   model adı ve max-tokens, prompt render, cevabın doğrulanması.
2. `llm/LlmChatClientConfig` — sağlayıcı başına **isimli** `ChatClient` bean'i;
   bean adı = `llm.provider`'ın seçtiği ad.
   ```java
   @Bean(ANTHROPIC)   ChatClient anthropicChatClient(AnthropicChatModel m)  { return ChatClient.create(m); }
   @Bean(OPENROUTER)  ChatClient openRouterChatClient(OpenAiChatModel m)    { return ChatClient.create(m); }
   ```
   `ChatClientLlmClient` bunları `Map<String, ChatClient>` olarak alır. Yeni
   sağlayıcı eklemek = buraya bir `@Bean` + config'e bir `llm.providers` girdisi;
   `ChatClientLlmClient`'a dokunulmaz.
3. Options **generic** kurulur: `ChatOptions.builder().model(m).maxTokens(t)`.
   Sağlayıcıya özel options kodu hiçbir yerde tutulmaz — gerekçe "Tuzaklar"da.
4. Hatalar: `LlmDisabledException` (katman kapalı), `UnknownLlmProviderException`
   (`llm.provider` kayıtlı değil, mesajda kayıtlı adlar), `LlmProviderUnavailableException`
   (`llm.providers.<ad>.model` yok), `LlmResponseException` (boş cevap / boş metin).
5. `llm/LlmProperties` sağlayıcı bazlı:
   ```yaml
   llm:
     enabled: true
     provider: openrouter         # anthropic | openrouter
     providers:
       anthropic:
         model: claude-sonnet-5
         max-tokens: 3000
       openrouter:
         model: openai/gpt-5      # OpenRouter model kimliği: <sağlayıcı>/<model>
         max-tokens: 3000
   spring:
     ai:
       anthropic:
         api-key: ${ANTHROPIC_API_KEY:}
       openai:
         base-url: https://openrouter.ai/api/v1
         api-key: ${OPENROUTER_API_KEY:}
   ```
6. `pom.xml`: `spring-ai-starter-model-openai` (sürüm BOM'dan).

## Doğrulama

- `./mvnw test` — birim testleri + anahtarsız context testleri
- `ANTHROPIC_API_KEY` ile `ChatClientLlmClientAnthropicLiveTest`: gerçek çağrı,
  JSON parse
- `OPENROUTER_API_KEY` ile `ChatClientLlmClientOpenRouterLiveTest`: **yalnızca**
  `llm.provider=openrouter` değişikliğiyle aynı prompt farklı sağlayıcıdan döner
- Hiç anahtar yokken uygulama açılır; yalnızca `ask()` hata verir

## Tuzaklar

- `ObjectProvider<ChatModel>` **kullanılamaz**. Anthropic ve OpenAI
  autoconfig'lerinin ikisi de `spring.ai.model.chat` için
  `matchIfMissing = true` taşıyor; iki starter birlikteyken **iki** `ChatModel`
  bean'i oluşur ve tek bir `ChatModel` istemek `NoUniqueBeanDefinitionException`
  ile patlar. Sağlayıcı bean'leri beton tipleri (`AnthropicChatModel`,
  `OpenAiChatModel`) istemeli.
- `spring.ai.openai.api-key` **boş string** olarak verilmeli. Boş string
  bilinçli bir "no-auth" sinyali (Authorization header'ı sıyrılır); `null`
  kalırsa OpenAI SDK'nın credential doğrulaması açılışta patlar ve anahtarsız
  makinede context hiç açılmaz.
- Generic `ChatOptions.Builder`'ın yeterli olmasının nedeni: `ChatClient` isteği
  kurarken options'ı **modelin kendi** builder'ından başlatıyor
  (`chatModel.getOptions().mutate()`), bizim builder'ı `combineWith` ile üstüne
  bindiriyor. Yani nihai tip her zaman sağlayıcının tipi
  (`AnthropicChatOptions` / `OpenAiChatOptions`); biz yalnızca `model` ve
  `maxTokens` değerlerini yazıyoruz. Bu şart: `OpenAiChatModel` içinde
  `(OpenAiChatOptions) prompt.getOptions()` diye sert bir cast var.
- `ChatClient`'ın `options(...)` metodu kurulmuş `ChatOptions` değil bir
  `ChatOptions.Builder` alıyor.
- Testlerde `chatModel.getOptions()` stub'lanmak zorunda; nihai options oradan
  türetildiği için stub yoksa NPE gelir.

## Kararlar

- İlk hal `LlmClient` arayüzü + `RoutingLlmClient` + sağlayıcı başına istemci
  sınıfı şeklindeydi; aynı `ask()` sözleşmesini hem yönlendirici hem sağlayıcı
  taban sınıfı taşıdığı için iki paralel hiyerarşi oluşuyordu. Hepsi kaldırıldı:
  tek beton sınıf (`ChatClientLlmClient`) + isimli `ChatClient` bean'leri. Model
  belirleme ve yönlendirme aynı yerde durduğu için akış tek dosyada okunuyor.
- Sağlayıcı seçimi `@ConditionalOnProperty` ile yapılmadı; tüm `ChatClient`
  bean'leri kayıtlı kalıyor, hangilerinin var olduğu açılış logunda görünüyor ve
  provider değiştirmek context'i yeniden kurmayı gerektirmiyor.
- Çağrı bazında model override'ı (`ask(..., provider)`) eklenmedi; SP001'in
  isteri "kod değişikliği olmadan değiştirilebilmeli", bu da config ile
  karşılanıyor. `ask()` imzası T001_0'daki gibi kaldı.
- `spring.ai.model.chat` set edilmiyor; iki `ChatModel` bean'i birlikte
  yaşıyor ve seçim `llm.provider` ile yapılıyor. İki ayrı anahtarın
  (`spring.ai.model.chat` + `llm.provider`) birbirine uyması gerektiği tuzağı
  böylece hiç doğmuyor.
- `ChatClient` bean'leri eager kuruluyor (tembel `SingletonSupplier` kalktı):
  `ChatClient.create(...)` API'ye gitmediği ve iki `ChatModel` bean'i her zaman
  var olduğu için sorun değil. `spring.ai.model.chat` ile biri kapatılırsa hata
  artık `ask()` anında değil açılışta gelir — bilinçli.
- `LlmProperties.providers` anahtarları ve `ChatClient` bean adları küçük harfe
  normalize ediliyor; `llm.provider=OpenRouter` de çalışıyor.
- Sağlayıcı bean'leri `llm/` içinde, `config/` paketinde değil: bunlar
  cross-cutting altyapı değil, model erişim katmanının kendi kablolaması.
- Testler: `ChatClientLlmClientTest` iki mock `ChatModel` (arayüz mock'u, `final`
  sınıf mock'lamaya gerek yok) üstünde kurulu iki `ChatClient` ile yönlendirmeyi,
  büyük/küçük harf duyarsızlığını, kapalı katmanı, bilinmeyen sağlayıcıyı ve
  **options tipinin sağlayıcıya göre değiştiğini** doğruluyor.
  `LlmProviderContextTest` iki `ChatClient` bean'inin kayıtlı olduğunu görüyor.
- SP005/SP006'da yazılan `FindingEnricherTest` ve `AnalysisServiceTest`,
  `LlmProperties`'in eski üç alanlı halini kullandığı için derlenmiyordu (PR #8
  iki tarafı derlemeden birleştirmiş); fixture'lar yeni kurucuya çevrildi.
- OpenRouter üzerinden **gerçek** çağrı henüz koşulmadı: bu makinede
  `OPENROUTER_API_KEY` tanımlı değil. Kalan tek doğrulama adımı bu.
